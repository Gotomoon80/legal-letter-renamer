# 鸿蒙（HarmonyOS）移植准备说明

> 目标：现阶段用**最小改动**，为后期适配/上架鸿蒙平台预留空间，不做过度设计。

## 一、为什么不能"直接把 exe 搬到鸿蒙"

鸿蒙 NEXT（HarmonyOS 5）只支持 **ArkTS / ArkUI** 开发，通过 DevEco Studio 打包为 `.hap`，
不再兼容 Android APK，也没有官方的 Python 运行环境。因此：

- 界面（Tkinter）**不可能**在鸿蒙上运行，将来必须用 ArkTS 重写界面；
- 但**业务逻辑（解析、匹配、模板、计划、撤销）是纯 Python**，具备复用价值。

## 二、已经做好的准备工作（v1.0.1）

### 1. 核心与界面彻底解耦

- `src/core/` 下**没有任何一行代码 import GUI 库**，可在无界面环境运行；
- 依赖仅 `openpyxl`、`xlrd`（均为**纯 Python**，无 C 扩展），极易移植；
- 界面 `src/ui/` 只"调用"核心，不含业务规则。

### 2. 全部核心数据结构可 JSON 序列化

`src/core/serializer.py` 为以下结构提供 `to_dict / from_dict / to_json`：

| 结构 | 含义 |
| --- | --- |
| `FileItem` | 扫描到的文件属性 |
| `ParsedName` | 文件名解析结果（序号/姓名候选/占位符） |
| `RosterEntry` | 名单一行 |
| `MatchItem` | 匹配结果 |
| `PlanRow` | 重命名计划一行 |

### 3. 提供"跨语言接口契约层"

`src/core/api.py` 提供纯函数式、输入输出全 JSON 的接口：

```python
from core import api

result = api.pipeline({
    "folder": r"D:\待处理",
    "roster_path": r"D:\客户名单.xlsx",
    "roster_text": "",              # 也可直接粘贴姓名，每行一个
    "mode": "by_name",              # 或 by_order
    "sort": "name_asc",
    "groups": ["Word", "Excel"],
    "all_types": False,
    "recursive": False,
    "fallback": True,
    "template": "{序号}_{姓名}_律师函",
    "seq_start": 1,
    "seq_width": 4,
    "replace_in_orig": False,
})
# result["rows"] 即前端可直接展示的重命名计划（含状态中文说明）

api.execute_plan(result["rows"])     # 执行
api.undo_last()                      # 撤销
```

**这份 JSON 契约就是鸿蒙前端的对接标准**：将来 ArkTS 界面只要按照
`pipeline / execute_plan / undo_last` 三个入参、出参结构，即可与核心一致地工作。

## 三、将来切换鸿蒙的三条可选路线

| 路线 | 做法 | 适用 |
| --- | --- | --- |
| A. 逻辑移植 | 按 `api.py` 契约，用 ArkTS 重写解析/匹配/模板逻辑 | 纯前端 App，最彻底 |
| B. 服务化 | 核心跑在服务端（PC/云），鸿蒙前端走 HTTP 调用同一套 JSON | 想在电脑上处理文件 |
| C. 内嵌解释器 | 通过 NDK 在 ArkTS 应用内嵌 CPython，直接跑 core | 技术门槛高，非必须 |

> 当前阶段推荐 **A**：因为核心逻辑清晰、依赖纯 Python，移植工作量可控。

## 四、编写新代码时请遵守的纪律

1. **不要**在 `src/core/` 里 import `tkinter` 或任何界面库；
2. 新增核心功能尽量只依赖 Python 标准库；
3. 新增的数据结构请在 `serializer.py` 里补上序列化支持；
4. 跨平台要用到的功能，统一在 `api.py` 暴露为 JSON 接口；
5. 避免使用 Windows 专有 API（如 `os.startfile`）——目前仅界面层使用，无碍移植。
